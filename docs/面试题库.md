## A. 开场 60 秒

### A1. 用一分钟介绍这个项目

答：我做的是高校独占场地预约后端。师生能查场地、看某天占用、提交和取消预约；管理员维护场地、查全部预约、在开始前取消。

难点不是增删改查，是同一场地同一时段不能被约两次。提交走事务：先锁用户再锁场地，再查配额、重复、相交，最后插入。正确性只信 MySQL，Redis 只缓存场地详情。

### A2. 你在里面负责什么？

答：独立完成后端。三张表、登录 JWT、用户预约和管理端、并发防超约、领域规则单测、Swagger 联调。

没有前端，用 Swagger / Postman 验收。

### A3. 最大的收获是什么？

答：亲眼看见「有行锁也会超约」——可重复读下无锁 COUNT 拿的是旧快照。后来分清了：锁管排队，隔离级别管读到哪一版数据。

### A4. 最大的不足是什么？（主动说，别等揭穿）

答：没有前端；Token 注销和刷新没做；压测是本机 PowerShell 脚本，不是 JMeter，也不等于我会 C#；错误码上配额检查在重复检查前面，满额时同一槽再约会先报配额而不是重复。

## B. 业务规则（最容易被举例追问）

### B1. 提交预约时按什么顺序校验？

答：先做不占锁的：场地是否存在/启用、时间是否半点对齐、是否在 7 天内、是否已过、是否在开放时间。再锁用户、锁场地。再查未结束是否已有 2 条、是否完全相同重复、是否和别人相交。最后插入 CONFIRMED。

先便宜校验、后加锁，缩短持锁时间。

### B2. 半开区间是什么？为什么用它？

答：时段按 [开始, 结束) ，开始算占用，结束那一刻不算。10:00–11:00 和 11:00–12:00 可以都成功。

好处是相邻能拼、长度好算。判断相交：`自己开始 < 对方结束 并且 自己结束 > 对方开始`。

### B3. 10:00–11:30 和 11:00–12:00 算冲突吗？

答：算。11:00 < 11:30 且 12:00 > 10:00，相交。唯一索引挡不住这种交叉，所以不能靠「场地+起止相等」唯一约束。

### B4. 为什么开始必须晚于现在？今天 10 点能约今天 10 点吗？

答：不能。`start > now`，已经开始的格子不让新约。约「正在进行」没有意义，取消规则也管不到。

### B5. 为什么最多提前 7 天？

答：产品冻结：避免把场地锁太远。实现是日期不能晚于今天加 7 天，再加一条开始时刻必须晚于现在。

### B6. 为什么必须整点或半点？

答：格子对齐，占用图和冲突都按 30 分钟算。10:10 直接 TIME_INVALID。秒和纳秒必须是 0。

### B7. 为什么不能跨天？

答：P0 一天一个开放窗口，跨天要把两天开放时间拼起来，规则变复杂。开始和结束是同一天的两个 LocalTime。

### B8. 配额「未结束」怎么定义？

答：状态是 CONFIRMED，并且结束时间还大于现在。进行中的也占配额。已取消、已过结束时间的不占。上限 2 条。

### B9. 进行中的预约占不占配额？能不能取消？

答：占配额，因为还没结束。用户取消要提前 2 小时，已经开始了不能取消；管理员也要求现在早于开始，已开始也不能取消。

### B10. 用户取消和管理员取消差在哪？

答：用户：现在必须不晚于开始前 2 小时。管理员：只要还没开始就能取消。都只能取消 CONFIRMED。已取消再取消会 CANCEL_NOT_ALLOWED。

### B11. 取消别人的预约，学生会看到什么？

答：按「找不到」处理，返回 RESERVATION_NOT_FOUND，不告诉他这单存在。避免用 id 扫别人的预约。管理员走另一条接口，可以取消任意未开始的单。

### B12. 停用场地后，旧预约怎么办？用户列表还看得到这个场地吗？

答：旧 CONFIRMED 不自动取消。用户列表只返回 ENABLED，停用的从列表消失。拿着旧 id 再约，返回 VENUE_DISABLED。提交时锁住场地后再查一次状态，防止刚停用还约上。

### B13. 占用接口返回什么？为什么不能拿它当「一定能约」？

答：那天的开放时间和所有 CONFIRMED 区间，只读、不加锁。看完再点提交，中间别人可能已经约上，所以最终听提交接口。

### B14. 我的预约四个 filter 怎么分？

答：UPCOMING：已确认且开始还没到。ONGOING：已确认且已经开始、还没结束。ENDED：已确认且已经结束。CANCELLED：已取消。不传 filter 就全部返回。

### B15. 学生和老师预约有什么差别？

答：P0 没有差别。角色只决定能不能进 /api/admin。管理员也能走用户预约接口，规则一样。

### B16. 为什么不物理删除场地？

答：预约有外键指着场地。停用就够了。删了历史预约对不上。

### B17. purpose 必填吗？

答：不必填，最长 100 字。空的存 null。

### B18. 同一人同一场同一起止已经取消过，能再约吗？

答：能。重复和冲突都只跟 CONFIRMED 比，取消过的不算占坑。

## C. 并发与事务（必会，换一种问法）

### C1. 画一下提交时加了几把锁？

答：两把现成行上的锁。用户行 FOR UPDATE，场地行 FOR UPDATE。不是去锁「还不存在的那条预约」。冲突 COUNT 也带 FOR UPDATE，是当前读。

### C2. 只锁场地、不锁用户，会出什么问题？

答：同一人同时约两块不同场地。两个事务各锁各的场地，配额查询都看到「未结束 0 或 1」，都能通过，最后这个人未结束变成 3、4 条。

### C3. 只锁用户、不锁场地呢？

答：两个人约同一场地同一时段。各锁各的用户，冲突查询可能都看到空，一起插入。场地超约。

### C4. 为什么先锁用户再锁场地？

答：所有事务统一顺序，避免死锁。如果 A 先锁场地 X 再锁用户 1，B 先锁用户 1 再锁场地 X，两人互相等。

### C5. 死锁是什么？MySQL 怎么办？

答：两个事务互相等对方手里的锁。InnoDB 会让其中一个报错回滚。我们用固定顺序降低概率，而不是靠捕获死锁重试（P0 没做重试）。

### C6. FOR UPDATE 加在事务外面有用吗？

答：没用。锁在事务提交或回滚时释放。没有 @Transactional，语句一结束锁就没了。

### C7. requireVenue 为什么还走普通 SELECT，不直接 FOR UPDATE？

答：先无锁读，做时间校验，不持锁。真要写再锁。但 RR 下这次普通 SELECT 会定快照，所以后来才改 RC，并且后面的 COUNT 改成当前读。

### C8. 快照是什么时候拍的？RR 下会换吗？

答：RR 下，本事务第一次普通 SELECT 生成 ReadView。事务不结束就不换。COMMIT / ROLLBACK 才结束。FOR UPDATE 不走这张快照，读最新已提交。

### C9. 只把隔离改成 RC，COUNT 仍是普通 SELECT，还会超约吗？

答：场地行锁还在的话，一般不会——第二条等第一条提交完再 COUNT，RC 这次 SELECT 能看见新行。没有行锁的话还会超约，两个人可以同时 COUNT 到 0 再一起插入。隔离级别不管互斥。

### C10. 真正拦住第二条请求的是什么？

答：两段。行锁让它排队，等到第一条提交。醒来后的当前读（或 RC 的新 ReadView）让它看见第一条插进去的行。只锁不换读法，或只换隔离不加锁，都不够。

### C11. 脏读、不可重复读、幻读用大白话说？

答：脏读：读到别人还没提交的修改。不可重复读：同一行两次读，中间被别人改了。幻读：一个范围内两次查，行数变了（多出别人新插入的行）。RR 用快照减轻后两种；我们防超约不靠快照，靠当前读加锁。

### C12. 为什么不用 SERIALIZABLE？

答：能防，但并发更差，间隙锁更多。RC + 行锁 + 当前读已经够这一个「检查再插入」的场景。

### C13. 连接池为什么 30？太小会怎样？

答：20 个事务同时要连接。池子 10 的话有人拿不到连接，超时或排队，压测数字会脏，看起来像冲突失败其实是池子不够。

### C14. 压测为什么必须 20 个不同账号？

答：同一账号未结束只能 2 条，20 路会先撞配额，看不出场地有没有约重。

### C15. 取消时为什么也要锁场地？

答：取消会把 CONFIRMED 改成 CANCELLED，等于释放坑。和提交抢同一场地时，避免一个在插、一个在改状态，两边都看走眼。先锁场地再读预约行。

## D. 表、SQL、索引（可能让你手写）

### D1. 冲突查询的 SQL 怎么写？

答：

```sql
SELECT COUNT(*) FROM reservation
WHERE venue_id = ?
  AND status = 'CONFIRMED'
  AND start_time < ?
  AND end_time > ?;
```

后两个问号分别是「我的结束」「我的开始」。

### D2. 为什么不建 UNIQUE(venue_id, start_time, end_time)？

答：只能挡住完全相同的起止，挡不住交叉重叠。10:00–11:30 和 11:00–12:00 两行值都不同，唯一索引都放行。

### D3. 有哪些索引？干什么用？

答：预约表 (venue_id, start_time, end_time) 给冲突和按场地查时间。 (user_id, status) 给配额和我的预约。用户名唯一。场地 (status, type) 给列表筛选。

### D4. 外键的作用？缺点？

答：预约不能指向不存在的用户或场地。代价是插入要检查、删场地会受限。我们本来就不物理删场地。

### D5. MyBatis-Plus 的 .last("FOR UPDATE") 是什么？

答：在生成的 SQL 末尾拼固定字符串。这里只拼常量。不要把请求参数拼进去，有注入风险。

## E. Redis

### E1. 读场地详情的完整路径？

答：先 Redis key `venue:detail:{id}`。有就反序列化返回。没有就查库，再写回 Redis，TTL 1 小时。Redis 抛错就当没有，走库。

### E2. 改场地名称后缓存怎么办？

答：先更新数据库，再删这个 key。下次读 miss，读到新名称再回填。不在 Redis 里改一份，避免和库不一致。

### E3. Cache Aside、Write Through 有什么差别？

答：我们是 Cache Aside：应用自己管缓存，读 miss 回源，写库后删缓存。Write Through 是写的时候缓存和库一起更新，组件更重。场地写很少，删缓存够用。

### E4. 缓存穿透、击穿、雪崩各是什么？本项目严重吗？

答：穿透：查不存在的 id，每次打到库。击穿：热点 key 过期瞬间全打到库。雪崩：大批 key 同时过期。场地详情量小、预约不走缓存，风险不大。没做空值缓存和单飞，被问到承认。

### E5. Redis 和 MySQL 的数据会短暂不一致吗？

答：会。删缓存和读并发时，可能读到旧值再写回。场地改名不是正确性路径，可接受。预约正确性不读这个缓存。

### E6. 为什么不用 Redis 做占用格子缓存？

答：占用每次预约都变。缓存错了，前端会画出能约，提交再失败，体验差还解释不清。收益小。

## F. 登录与权限

### F1. JWT 三段是什么？哪一段不能信？

答：头、载荷、签名。载荷 Base64 能解开，谁都能看见，不能放密码。改完载荷对不上签名，Filter 当无效，最后 401。

### F2. 登录成功后服务端存 Session 吗？

答：不存。STATELESS。每次请求带 Authorization: Bearer token，Filter 验签后放进 SecurityContext。

### F3. JwtAuthFilter 放在哪？坏 token 怎么处理？

答：放在 UsernamePasswordAuthenticationFilter 前面。验签失败就清空上下文，不自己写 401，让后面的鉴权判定「没登录」，由 JSON 的 401 处理器返回 UNAUTHENTICATED。

### F4. hasRole("ADMIN") 和库里的 ADMIN 怎么对上？

答：LoginUser 的权限是 `ROLE_` 加角色名，也就是 ROLE_ADMIN。Spring 的 hasRole 会自己补 ROLE_ 前缀。

### F5. 为什么关 CSRF？

答：浏览器 Cookie Session 才怕跨站带 Cookie 提交。我们是前端自己放 Header 的 JWT，没有 Session Cookie，CSRF 不是这条链路的问题。

### F6. 密码为什么用 BCrypt 不用 MD5？

答：BCrypt 不可逆、自带盐、算得慢，撞库成本高。MD5 太快，彩虹表能破。种子数据先写 PENDING_BCRYPT，启动时再写成 123456 的哈希。

### F7. Token 有效期多久？过期后怎么办？

答：86400 秒，一天。过期只能重新登录。没做 refresh，也没做登出黑名单。登出只是前端扔掉 token。

### F8. 水平越权和垂直越权在本项目的例子？

答：水平：学生 A 拿学生 B 的预约 id 去取消，我们比 userId，当找不到。垂直：学生调管理端建场地，403。

## G. Spring 工程

### G1. 一次预约请求经过哪些层？

答：JwtFilter 验 token → Controller 收 JSON 并 @Valid → ReservationService 开事务 → Mapper 访问 MySQL。出错走 GlobalExceptionHandler，包成 {code, message, data}。

### G2. @Transactional 加在 Controller 上行吗？

答：能跑但不合适。事务边界应包住「锁、查、写」这一段业务，不要把 HTTP 序列化算进事务。我们加在 Service 的 create / cancel 上。

### G3. 构造器注入和字段 @Autowired 差在哪？

答：构造器注入依赖都是 final，测的时候好传 Mock，启动时缺 Bean 立刻失败。本项目全是构造器注入。

### G4. Bean Validation 失败返回什么？

答：PARAM_INVALID，HTTP 400。例如 venueId 空、purpose 超过 100 字。

### G5. 业务异常和系统异常怎么区分？

答：业务抛 BusinessException，带 ErrorCode，按对应 HTTP 返回。没料到的 Exception 打日志，返回 500 INTERNAL_ERROR，不把堆栈给前端。

### G6. CONFLICT 为什么是 409 不是 400？

答：请求格式没问题，是资源和别人冲突。400 表示你这单本身不合法；409 表示现在这个坑被占了。

### G7. MyBatis-Plus 和手写 XML 比，你用它做什么、不做什么？

答：列表、按 id 查、插入、更新用 BaseMapper 和 LambdaQueryWrapper。带 FOR UPDATE 的按主键锁，手写了一句 @Select。复杂报表没做。

## H. 方案对比（面试官爱抬杠）

### H1. 为什么不上 Redis 分布式锁？

答：正确性已经在 MySQL。SETNX 过期或 Redis 挂了会误放行。多实例连同一库，行锁仍然有效。分布式锁以后做多资源、跨库再考虑。

### H2. 为什么不上消息队列？

答：没有支付超时关单，也没有异步通知。预约是同步要么成功要么失败。上 MQ 会多出最终一致和重复消费，P0 不需要。

### H3. 两个实例部署，行锁还有效吗？

答：有效。锁在 InnoDB，不在应用内存。两台机器连同一个 MySQL，仍然互斥。分库分表把预约拆开才会失效。

### H4. 如果以后要做自习室按座位共享，现在这套哪会坏？

答：冲突模型是整场独占。自习室要改成「容量/座位」，COUNT 相交不再等于超约，锁粒度也要从场地行变成座位或库存。P0 刻意没做。

### H5. 如果要加审批，状态机怎么扩？

答：会多 PENDING。必须先定：待审占不占坑。占坑别人约不了；不占坑一审多份会超约。这是另一条产品线，P0 提交即 CONFIRMED。

### H6. 压测脚本为什么是 PowerShell 调 HttpClient，不是 Java？

答：本机是 Windows，图的是同时发出 20 个 POST。不是 C# 项目，我也不会把它写成技术栈。价值在验收：20 个账号、同一时段、数 OK 和库 COUNT。重做可以用 Java 线程或 JMeter。

## I. 手写题（张嘴就能写）

### I1. 相交函数

答：`return start.isBefore(otherEnd) && end.isAfter(otherStart);`

### I2. 用户能不能取消

答：必须是 CONFIRMED。如果现在晚于 `start 减 2 小时`，不行。

### I3. JWT Filter 四步

答：取 Authorization。不是 Bearer 就放行（后面当没登录）。验签取出 userId、角色。放进 SecurityContext。验失败就清空，继续 filterChain。
