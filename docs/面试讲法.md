# 面试讲法（对照当前代码）

核心一句话：**预约能不能约上只信数据库事务，Redis 只加速场地详情读取。**

提问清单、要背的原理见 [面试准备.md](面试准备.md)。  
题库（问答直接背）见 [面试题库.md](面试题库.md)。

## 1. 防超约怎么做的

提交顺序：校验时间 → 锁用户行 → 锁场地行 → 查配额/重复/相交 → 插入 `CONFIRMED`。

- 锁用户：避免同一人同时约两块场地突破「未结束 ≤ 2」。
- 锁场地：同一场地的提交串行化。
- 相交条件：`start < otherEnd AND end > otherStart`（半开区间，11:00 接下 11:00 不算冲突）。

代码：`ReservationService.create`，冲突 SQL 在配额/重复查询之后。

## 2. 面试官追问：第一次并发为什么会超约

MySQL 默认 **可重复读**。事务里第一次 `SELECT`（查场地）就定了快照，后面无锁的 `COUNT` 看不见别人已经提交的预约，20 路里曾经插入了 12 条。

改法：

- 事务隔离改为 `READ_COMMITTED`
- 配额/重复/冲突查询加 `FOR UPDATE`，读最新已提交数据

验收：`scripts/ac4-concurrent.ps1`，20 个不同用户同时约同一槽，成功 1、冲突 19。

不要说「靠 Redis SETNX 防超约」——Redis 挂了会误放行；本项目行锁才是正确性来源。

## 3. Redis 用在哪、不用在哪

- **用：** `GET /api/venues/{id}`，Cache Aside，key `venue:detail:{id}`，TTL 1 小时；更新场地时删缓存。
- **不用：** 占用查询、提交预约。`requireVenue` 仍走数据库，停用/冲突以库为准。
- Redis 宕机：`VenueCache` 吞掉异常回源 DB，预约不受影响。

## 4. 为什么还没上 MQ / 分布式锁

- 没有支付超时单，通知可以后补。
- 单机或多实例只要连同一 MySQL，InnoDB 行锁仍然有效，不必先上 SETNX。
